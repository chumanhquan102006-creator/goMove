# GoMove Flutter

The app defaults to mock authentication for the existing UI tests. For the real Customer flow on a standard Android emulator, run from `mobile/`:

```powershell
flutter pub get
flutter run -d emulator-5554 --dart-define=MOCK_ENABLED=false --dart-define=API_BASE_URL=http://10.0.2.2:8080
```

`API_BASE_URL` may be the server origin or an origin ending in `/api/v1`; it is normalized once. For a remote HTTPS deployment, pass its HTTPS origin instead. `WS_BASE_URL` optionally overrides the realtime `/ws` endpoint; by default it follows the API host (`ws://10.0.2.2:8080/ws` on an Android emulator). Do not put credentials or JWTs in dart-defines.

The Customer booking screen starts over Hanoi. Search for a real place in **Điểm đón** or **Điểm đến**, select a returned suggestion, or choose a point on the map to look up a nearby address. The blue outlined pickup marker, orange destination marker and coordinate cards show which point changed. **Xem 2 điểm** fits the camera to both valid markers. Manual latitude/longitude entry remains available when search, reverse lookup, the map style or tiles fail. A missing address is shown as unavailable; coordinates remain the Quote input and are never replaced by a guessed street name. After a new Quote is issued, its review screen retrieves the authorized, stored OSRM road geometry and draws a blue street-following line when available. The map never joins the two markers to invent a route. OSRM road distance, duration, fare, Quote UUID and expiry come only from the backend. Quote confirmation uses the backend's `expiresAt` and `finalFare`; local countdown is advisory. After a network timeout, retry the persisted Booking intent with the same idempotency key. The pending-intent card lets the same Customer explicitly abandon it only after considering whether the previous request may have succeeded.

The default demonstration basemap is [OpenFreeMap Liberty](https://openfreemap.org/quick_start/), loaded by the existing `maplibre_gl` dependency. Override its style URL with `--dart-define=MAP_STYLE_URL=https://your-host/style.json` when an approved provider or self-hosted style is available; for a custom provider also set `--dart-define=MAP_ATTRIBUTION=...` to show its required credit (and keep the style's native attribution metadata). Before native map creation, the app sets an identifying `GoMoveAcademicDemo/1.0` User-Agent for MapLibre requests; if this setup fails, it leaves the map unavailable and keeps manual entry usable. Keep provider/OSM attribution readable; the map's native attribution button and the on-screen credit must not be obscured. [OpenFreeMap terms](https://openfreemap.org/tos/) provide the public service as-is and may change or discontinue it. This app does not prefetch/offline-download tiles or add JWT, Booking UUID or account data to tile URLs. The viewed map area is nevertheless requested from an external tile provider; see its [privacy policy](https://openfreemap.org/privacy/). Do not substitute the public `tile.openstreetmap.org` server as an unlimited production fallback; follow the [OSMF tile policy](https://operations.osmfoundation.org/policies/tiles/). A blank basemap can occur after a style loads because MapLibre 0.27.1 has no tile-error callback; use the manual-coordinate fallback and continue the same Backend Quote flow.

The Android scaffold is generated with Flutter 3.47.5. Internet permission applies to all builds; cleartext HTTP is allowed in debug/profile manifests only for local emulator development. Release remains HTTPS-ready. A running backend, its PostgreSQL and OSRM dependencies, and an existing Customer account are needed for an end-to-end smoke test.

To enter Vietnamese names on the Android emulator, enable Vietnamese in Gboard: open Android Settings → System → Keyboard (or Languages & input) → On-screen keyboard → Gboard → Languages → Add keyboard → Vietnamese. Switch languages with the globe key or by holding the space bar. The registration name field uses the system name keyboard and retains composed/decomposed Vietnamese characters; no app-specific keyboard is needed.

## M2 Driver dispatch demo

Run real mode with the command above. Use a separate Customer and Driver account. A Customer can open **Đăng ký làm tài xế**, submit a real license number to `POST /api/v1/drivers/onboarding`, then must sign out and sign in again to obtain a DRIVER JWT. The resulting profile is PENDING/OFFLINE; the app never self-approves it.

Approval requires an already legitimately provisioned ADMIN account. In real mode, that account opens the Admin dashboard and Driver queue, inspects the registered vehicle, and confirms approval or rejection. The existing `PATCH /api/v1/drivers/{driverPublicId}/approval-status` remains the Backend action. There is no public Admin registration or default Admin password. For isolated local development, the project lead must deliberately provision an existing account as ADMIN using a trusted local database administration procedure, then sign out and sign in again to obtain a fresh ADMIN JWT. Never run that procedure against a shared demo or production database; do not put credentials or JWTs in source, scripts, dart-defines or screenshots. Without a provisioned Admin account, the real approval E2E remains blocked.

For a **separate local development database only**, the project lead may create a fresh Customer account through normal registration with a personally chosen strong password, record its public UUID from the authorized response, verify the target database host/name, then run this one-time statement in an interactive `psql` session. Replace the UUID through `\set`; the statement changes exactly one unused, active Customer account and must return one row. Run `COMMIT;` only after checking that one row was returned; otherwise run `ROLLBACK;` and investigate. Log out and log back in so the JWT carries `ADMIN`.

```sql
\set admin_public_id 'replace-with-new-account-public-uuid'
BEGIN;
UPDATE users SET role = 'ADMIN', updated_at = CURRENT_TIMESTAMP, version = version + 1
WHERE public_id = :'admin_public_id'::uuid AND role = 'CUSTOMER' AND status = 'ACTIVE'
  AND NOT EXISTS (SELECT 1 FROM drivers d WHERE d.user_id = users.id)
  AND NOT EXISTS (SELECT 1 FROM bookings b WHERE b.customer_id = users.id)
RETURNING public_id, role;
```

Do not use this procedure on a shared demo or production database. It is intentionally not an application endpoint, automatic startup seed or hardcoded credential.

After approval, sign in as DRIVER, add a matching vehicle, activate it, and press ONLINE. The app uses Android foreground location only: grant location permission, enable device location, and for emulator GPS set a position near the Customer pickup (within the backend's 5 km dispatch radius) in Android Studio **Extended Controls → Location**. The app does not hardcode its GPS position. Approximate permission may reduce eligibility. GPS is uploaded immediately and every 9 seconds while foreground/ONLINE or BUSY; active offers are polled every 2 seconds while foreground/ONLINE with a fresh GPS upload (<30 seconds). On the active M3 trip screen, authorized ride-channel GPS replaces the BUSY profile heartbeat while realtime is connected; the profile heartbeat is a disconnected fallback. Backgrounding stops both loops and does not force BUSY to OFFLINE. Foreground resumption revalidates ONLINE with the server.

The offer card shows the server-provided `expiresAt`; local countdown only disables late taps, and server 409 remains authoritative. Accept/Reject are sent once for the offer UUID. If a response is lost, the app checks authorized Booking tracking and never blindly repeats a decision. A confirmed accept shows the original offer's Booking UUID, coordinates, vehicle type and fare and the server-confirmed BUSY state. That handoff is stored per account and rechecked against tracking on restart. No Driver profile-read or current-assignment-list endpoint exists, so after a fresh start with no saved handoff the current operating status is **Chưa xác định** until a server status response; app-data deletion cannot recover an assignment. Trip transitions, cash and WebSocket tracking are intentionally not part of M2.

For a real dispatch smoke test, start PostgreSQL/PostGIS, Spring Boot with dispatch enabled, and OSRM for Customer Quote. Use two Android emulators or devices with separate accounts. Have the approved Driver ONLINE with an active matching vehicle and fresh GPS near pickup; then have the Customer create a new Booking. Accept the single offer within its 15-second server lease and confirm the Customer Booking transitions to `DRIVER_ACCEPTED`. Without the prerequisite accounts/services this is a checklist, not evidence of an executed end-to-end test.

## M3 trip lifecycle and CASH

The accepted-Booking handoff opens the Driver trip screen. Its four buttons follow only the server-confirmed state: arrive, onboard, start, then complete. Completion does **not** release the Driver. Once tracking says `COMPLETED` and the CASH payment is still `PENDING`, the Driver must explicitly confirm that cash was physically collected. The Backend returns a `PAID` receipt, accrued commission receivable and `driverReleasedAt`; the commission shown is owed to the platform, **not** proof of remittance. A lost cash-confirm response is reconciled with `GET /bookings/{id}/payment`; for `PAID`, the assigned Driver can explicitly retrieve the original durable receipt by replaying the same confirm endpoint. A `COMPLETED` unpaid handoff remains account-scoped in secure storage across restart/login.

Customer and Driver subscribe to the active Booking's `/topic/ride/{UUID}` using a JWT in STOMP CONNECT headers. Only the Driver sends fresh foreground GPS to `/app/ride/{UUID}/location`. Realtime is best effort; both screens reconcile with REST and show the connection state. A completed trip immediately hides all Driver GPS, while Customer payment polling continues until `PAID`. Backgrounding or leaving a trip screen disconnects and stops trip GPS. A rotated token reconnects with a fresh JWT and rechecks REST. If app data or the accepted handoff is lost, the Driver cannot discover an old assignment because the Backend has no current-assignment-list endpoint.

For manual two-emulator verification, use separate Customer and approved Driver accounts and the same real Booking UUID on both screens. From an existing accepted Booking, press each Driver action in order and verify Customer status/timestamps after each. During an active trip, move emulator GPS and verify the Customer sees an updated coordinate and server timestamp. Complete the trip and verify GPS disappears but payment remains `PENDING` and Driver remains `BUSY`. Only after physically collecting cash, confirm in the Driver dialog; verify receipt, `PAID` on the Customer, and Driver release to `ONLINE`. Do not reset PostgreSQL or manually change financial rows. This procedure is not evidence of an executed E2E run.

## M3.1 Customer Booking recovery

After a confirmed Booking creation, the Customer app saves its public UUID as an account-scoped navigation reference. On login, restart, and foreground resume, the Customer home screen rechecks that UUID with the authorized `GET /api/v1/bookings/{bookingPublicId}` before showing trip details. This reference is separate from the pending Booking intent and its idempotency key; it never creates a Booking or proves ownership by itself. A completed trip with CASH `PENDING` remains available. CASH `PAID` shows the verified final state without offering it as an active trip.

For a Booking made before this reference existed, sign in as its Customer, choose the existing-Booking UUID recovery option on the home screen, and enter the public UUID from the original confirmed Booking response. The app saves an active or unpaid Booking only after the Backend confirms the current Customer can read it. An already PAID Booking shows its final state without replacing the saved reference to another ongoing trip. A missing or unauthorized UUID is rejected. Do not use this field to make a new Booking or modify Backend data.

## M4.2 Customer live tracking map

The Customer Booking status screen shows a MapLibre driver marker only when the authorized Tracking REST response or the existing ride-channel subscription supplies a valid, timestamped GPS fix for an active trip. The first fix centers the map. Later, strictly newer fixes move that same marker without changing the Customer's pan or zoom; **Tìm tài xế** recenters on request. The map defaults to page-scroll mode; enable map interaction to pan or pinch, then turn it off to scroll easily to CASH. The coordinate, accuracy, timestamp, realtime/REST status and CASH details remain readable if the map style or tiles fail. The map uses the same `MAP_STYLE_URL`, `MAP_ATTRIBUTION`, User-Agent and native attribution behavior as the Customer booking map. No separate GPS subscription, background tracking, location history or tile prefetch is added.

`GET /api/v1/bookings/{bookingPublicId}/tracking` exposes only the current authorized Driver fix. The Customer trip screen separately reads the owned Quote for the pickup/dropoff markers and `GET /api/v1/bookings/{bookingPublicId}/route` for the immutable street route. The live Driver marker disappears immediately on completion or session loss; a previously authorized static route and the trip/CASH details can remain visible. If geometry is unavailable or its request fails, the point markers and Booking/CASH flow continue without a line.

## Stored road route geometry (Flyway V14)

Quote creation requests GeoJSON geometry in the **same OSRM response** used for distance, duration and fare. V14 stores the validated LineString on the Quote; Booking reads its accepted Quote's snapshot. `GET /api/v1/quotes/{quotePublicId}/route` is available only to the owning Customer. `GET /api/v1/bookings/{bookingPublicId}/route` is available only to the owning Customer or assigned Driver. Both require the caller's JWT. Older Quotes without a captured route return `UNAVAILABLE`; the app does not reroute or fabricate a line. The Driver trip map retains the offer's pickup/dropoff markers, and the Customer map retains the owned Quote's points. **Xem tuyến** / **Xem 2 điểm** fit the camera only when tapped; map polling does not override the user's pan or zoom. Backend routes and live GPS are separate data sources.

For a one-emulator check, keep the already configured Backend, PostGIS and local Hanoi OSRM running, then launch the Customer app in real mode. Select two reachable Hanoi points, request a **new** Quote after V14, and confirm the review map shows a road-following line and both point markers. Pan/zoom, then verify ordinary UI changes do not move the camera; use **Xem 2 điểm** to recenter deliberately. Create the Booking once, open its status screen, and verify the same route and points while CASH/status remain readable. A pre-V14 Booking is expected to show points without a line. To check the Driver view on the same emulator, use an already legitimately assigned Booking: sign out, sign in as that assigned Driver, open the accepted trip, and verify the route and point markers. Do not modify PostgreSQL rows or reuse a Customer JWT for the Driver. A single emulator cannot demonstrate simultaneous live Customer/Driver GPS movement; that remains a separate device test.

For a two-emulator check, keep the approved Driver on emulator-5554 and the owning Customer on emulator-5556, both in real mode against the same Backend/Booking. During `DRIVER_ACCEPTED` through `IN_PROGRESS`, move the Driver emulator's location and verify that the Customer map marker and textual timestamp update, while a manually panned/zoomed map stays put until **Tìm tài xế** is tapped. Briefly interrupt realtime and verify REST reconciliation; then complete the trip and check that the map/GPS disappear immediately while CASH `PENDING` remains visible. Confirm cash to reach `PAID`, then sign out or switch accounts and verify the previous map never returns. A non-owning Customer must not be able to recover the Booking UUID through the authorized Backend endpoint. This is a manual checklist, not a claim of a completed device E2E run.

## M5.1 place search and address display

The Backend proxies bounded place search and reverse lookup through [Photon](https://photon.komoot.io/), which uses OpenStreetMap data. An authenticated Customer searches through `GET /api/v1/locations/search?q=...`; an authenticated Customer or Driver resolves a selected coordinate through `GET /api/v1/locations/reverse?latitude=...&longitude=...`. The app debounces typing, requests at most five suggestions, and reverse-geocodes intentional map selections rather than map pans. The Backend also limits each authenticated account to 30 combined geocoding requests per 60 seconds by default (`GEOCODING_MAX_REQUESTS` and `GEOCODING_RATE_WINDOW` configure this); the in-memory limit resets on Backend restart and is per instance. A limit breach returns 429 while manual coordinates remain usable. The public Photon instance is appropriate only for light academic demonstration traffic; it has no availability guarantee. For sustained or larger traffic, arrange an approved provider or self-hosted Photon instance and configure the Backend's `GEOCODING_BASE_URL`. These settings are server-side, not mobile keys. Keep the returned `© OpenStreetMap contributors` attribution visible with address results and follow the provider's current usage policy.

Only search text or selected latitude/longitude is sent from the Backend to Photon. The proxy does not forward mobile JWTs, account identifiers, Booking UUIDs or contact details. Do not enter personal or secret data into the search box. A timeout, rate limit, provider failure, empty result or unknown street leaves manual coordinates and the existing Quote/Booking flow usable. Search results are display metadata; Quote, OSRM route and fare still use the exact selected coordinates. The app does not persist address labels in Quote or Booking. On a recovered trip it resolves the authorized Quote coordinates again, so a nearby place label can differ from the original search selection or become unavailable; older Bookings remain readable with coordinates. Driver addresses appear only after the existing assigned-Booking tracking check.

## M4.5A journey ETA

The Customer trip sheet reads `GET /api/v1/bookings/{bookingPublicId}/eta` with the current authenticated session. In `DRIVER_ACCEPTED` it labels the Backend's OSRM road estimate as approximate pickup time and distance; in `IN_PROGRESS` it labels the estimate as approximate remaining road travel. Searching, arrived, onboard and completed states continue to use confirmed trip status and timestamps without an invented countdown. ETA never changes accepted fare or CASH state, and no ETA result moves the Driver marker or map camera.

The app requests ETA immediately on entering an eligible status, then at most once every 15 seconds while foregrounded. The Backend validates GPS age (at most 30 seconds) and accuracy (at most 100 m), reuses a recent estimate for movement below 50 m, limits OSRM refreshes to at least 15 seconds apart, and expires an estimate after 30 seconds. Every response includes server `servedAt`; the Customer card uses `expiresAt` minus `servedAt` with a local monotonic timer, so tablet clock skew cannot extend the display. It hides a result at expiry, on a status/session change, in the background, or after a failed authorized read. Resume requires a new session-bound read. Missing/stale/inaccurate GPS, unavailable routing or REST failures show a neutral ETA message. STOMP disconnection keeps REST ETA available when Backend GPS is still fresh; the tracking card separately shows connection state. The UI does not count minutes down from an old response.

For a manual Nokia T20 Customer + Android Emulator Driver check, keep the existing Backend, PostGIS and Hanoi OSRM running. Sign in with separate Customer and approved Driver accounts, make the Driver ONLINE with fresh, accurate GPS, and create a new Booking from the Customer. After the Driver accepts, verify the Customer shows approximate pickup minutes and road distance with an update time. Change only the Driver emulator GPS using Android Studio location controls; after a meaningful move and the refresh interval, verify a new estimate while a manually panned Customer map stays in place. Press Arrived and Onboard and confirm the pickup ETA disappears without the Driver marker jumping. Press Start and confirm a destination ETA appears only with fresh GPS and a valid road route. Stop GPS or interrupt OSRM and verify the card becomes unavailable instead of counting down. Complete the trip and verify Driver GPS disappears, CASH remains `PENDING` until the Driver confirms physical collection, and the paid state remains server-confirmed. This is a checklist, not evidence of an executed device test.
